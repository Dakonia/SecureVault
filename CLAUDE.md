# SecureVault — project context

Настраиваемая **zero-knowledge платформа** защищённого обмена данными (white-label, продаваемая). Данные шифруются на клиенте, сервер хранит только шифротекст. Первый клиент — сеть ресторанов; каркас — под многих клиентов. Полная документация в [docs/](docs/), опорная карта — [docs/10-Платформа-архитектура-v2.md](docs/10-Платформа-архитектура-v2.md), точка входа [docs/README.md](docs/README.md).

## Продуктовое видение (v2)
- **Организация (tenant)** — один клиент = изолированная организация со своими пользователями, ролями, данными, ключами.
- **Два режима поставки:** SaaS (наше облако) и self-host (сервер клиента) — один софт, разная конфигурация. В обоих режимах хостер не может прочитать данные.
- **Сервер:** VPS сейчас, каркас переносим и на физ-сервер (усиление, не переделка).
- **Роли/права:** конструктор в UI (админ настраивает галочками), кворум «N из M» настраиваем, пресет «Ресторан» из коробки.
- **Входы:** пароль / флешка+passphrase / YubiKey — админ выбирает разрешённые per-роль. **Старт: пароль + обычная флешка; YubiKey не сейчас, но каркас заложен (подключаемый вход).**
- **Лицензии/платные функции:** офлайн-ключи, подписанные нашим ключом (без phone-home → без утечки использования).
- Темп: медленно, профессионально, обсуждать каждый шаг. Владелец не программист — объяснять просто, код на мне.

## Роли
- **30 директоров** — каждый сдаёт и видит только свой ресторан.
- **3 полных доступа** — видят все рестораны, ключи на YubiKey.
- **Мастер «2 из 3»** (Shamir) — опасные операции только вдвоём.

## Инварианты безопасности (нарушать нельзя — ломает всю модель)
1. Шифрование только на клиенте, ДО отправки. Сервер никогда не видит открытых данных.
2. На сервере нет приватных ключей и нет открытых данных — только непрозрачные blob.
3. Сервер не участвует в расшифровке ни на одном шаге.
4. Только проверенная крипта (libsodium / age). Никакой самописной криптографии.
5. Приватные ключи не покидают носитель (YubiKey/флешка), DEK и ключи затираются из памяти сразу после использования.
6. Изоляция ресторанов — техническая (нет конверта → нет DEK → нет данных), не «на доверии».
7. Нет публичного домена/SSL (Certificate Transparency), нет открытых портов. Доступ только WireGuard + SPA + mTLS.
8. Audit-log — append-only с hash-chain.

## Стек (зафиксировано в docs/02-Стек.md)
- Клиент: Tauri (Rust + React/TS), системный WireGuard.
- Крипта: age + age-plugin-yubikey (старт), libsodium (XChaCha20-Poly1305, X25519), Shamir «2 из 3».
- Сервер: Debian/Ubuntu LTS, LUKS2 + dropbear-initramfs, API на Rust (axum) или Go, PostgreSQL + MinIO/ФС, mTLS.
- Сеть: WireGuard + fwknop (SPA) + nftables (default-drop).
- Бэкап: restic + age (ключ хранится отдельно).

## Границы (зафиксировано с заказчиком)
- Ключи есть у людей — их могут **законно** потребовать. Техникой не закрывается и не обходится.
- Зарплаты/ФИО = персданные → хранение в РФ, ФЗ-152, доступ по журналу. Осознанный выбор в пользу юридической чистоты.
- Фото экрана — принятый риск, снижается водяными знаками.
- ❌ Внешние LLM-API (YandexGPT/Claude) на конфиденциальных данных не используем.

## Правило работы
Перед сдачей любого этапа сверяться с [docs/08-Чеклист-безопасности.md](docs/08-Чеклист-безопасности.md): не появился ли где-то открытый ключ или открытые данные на сервере.
