# 10 · Платформа — Архитектура v2

Документы 01–08 описывают первый сценарий (одна сеть ресторанов, жёсткие роли). Этот документ поднимает проект до уровня **настраиваемой продаваемой платформы** защищённого обмена данными. Рестораны — первый клиент, а не вся программа. Всё ниже — **надстройка** над теми же принципами zero-knowledge из 01–08, они остаются в силе.

## Главная идея: «Организация» (tenant)
Вводим понятие **организации** — это один клиент (компания). У каждой организации свои пользователи, роли, данные, ключи и, при желании, свой сервер и оформление. Данные разных организаций изолированы и криптографически, и логически.

```
Платформа
 └── Организация (клиент)            ← сеть ресторанов, юрфирма, клиника…
      ├── Пользователи
      ├── Роли и права (настраиваются админом)
      ├── Пространства (spaces)      ← «ресторан №7» = одно пространство
      │    └── Записи и файлы (шифротекст)
      └── Журнал действий (зашифрованный, свой у каждой организации)
```

«Изоляция ресторанов» из v1 обобщается в **изоляцию пространств**: нет конверта с ключом пространства → данные для тебя недоступны математически.

## Два режима поставки (поддерживаем оба)
Один и тот же серверный софт, разница — только в конфигурации.

| Режим | Кто держит сервер | Кому подходит | Особенность |
|---|---|---|---|
| **SaaS (наше облако)** | мы | клиенты без своей IT-службы | много организаций на одной инсталляции, строгая изоляция |
| **Self-host** | клиент | тем, кому нужен свой контур | клиент ставит наш софт, свои ключи, платит за лицензию |

Важно: **в обоих режимах мы (или хостер) не можем прочитать данные клиента** — сервер хранит только шифротекст. Это и защита клиента, и снятие ответственности с нас.

## Про VPS честно (важно понимать)
- Именно zero-knowledge делает VPS **допустимым**: провайдер VPS и даже взломанный сервер видят только «мусор».
- Шифрование диска (LUKS) на VPS защищает от кражи диска/снапшота, но **не** от злонамеренного хостера, читающего оперативную память. Поэтому мы **не полагаемся** на секретность сервера — вся секретность на стороне клиента.
- Физический сервер добавляет контроль над «железом» и памятью. Переход VPS → физ-сервер — это **усиление**, а не переделка. Каркас один.

## Клиент подключается к указанному серверу
Программа-клиент не «прибита» к одному серверу. При настройке в неё задаётся **профиль подключения** (адрес сервера + сертификат + параметры сети). Профилей может быть несколько.
- Для SaaS — профиль указывает на наше облако.
- Для self-host — на сервер клиента.
- Это же даёт возможность «мы скажем клиенту, куда подключаться».

## Конструктор ролей и прав (настраивает админ)
Вместо жёстких «директор/полный доступ/мастер» — **гибкая настройка в интерфейсе админа**:
- Создать роль, отметить галочками права: *сдавать / читать / править / комментировать / выгружать / управлять пользователями / опасные операции*.
- Ограничить роль конкретными пространствами.
- Для опасных операций — настраиваемый **кворум «N из M»** (по умолчанию 2 из 3).
- **Пресеты «из коробки»**: готовый набор «Ресторан» (директор/полный доступ/мастер), чтобы работало сразу; всё можно менять.

## Подключаемые способы входа (назначаются per-пользователь)
Три способа. Все три — один принцип (секретный ключ человека), разница только в том, **где ключ хранится и как разблокируется**:
- **Пароль** (ключ зашифрован паролем, Argon2id) — самый простой, самый слабый. Работает без железа.
- **Флешка + пароль** — тот же зашифрованный ключ, но на USB. Нет флешки → нет ключа (два фактора).
- **YubiKey** (FIDO2/PIV) — ключ внутри железки, не извлекается; нужен сам ключ + PIN + касание. Самый надёжный.

**Админ назначает способ каждому пользователю индивидуально** внутри своей организации (напр. директору — пароль, полному доступу — YubiKey). Архитектурно вход — подключаемый модуль, новые способы добавляются без переделки.

**Статус:** старт на способе «пароль» (железа пока нет); флешка и YubiKey подключаются тем же каркасом, когда появятся.

## Мастер-аккаунт (владелец организации) — центр управления
Верхний уровень — «пульт» владельца. Один на организацию (можно несколько доверенных лиц). Вход: логин + пароль (позже флешка/YubiKey).

**Что делает мастер-аккаунт:**
- Создаёт организацию и её пространства (например, рестораны).
- Создаёт профили пользователей; каждому назначает роль и способ входа (пароль / флешка / YubiKey).
- Настраивает права под каждую роль: читать только своё / читать всё / править / комментировать / выгружать / опасные операции.
- Выдаёт, меняет, отзывает и удаляет доступ (перевыпуск ключей при потере/увольнении).
- Видит все данные своей организации (у него full-access ключ) и контролирует журнал действий.

**Опасные операции** мастера (выгрузка всего, смена мастер-ключа, изменение доступа, добавление/удаление доверенных) — по кворуму: сейчас 1 подтверждение, позже настраиваемое «N из M».

**Как рождаются ключи и пароли — РЕШЕНО: мастер генерирует и хранит ключи всех.**
Мастер создаёт профиль, задаёт пароль/ключ и способ входа, может сбросить пароль и войти как любой пользователь. Проще в управлении. Плата за простоту — мастер-аккаунт становится единой точкой, где лежит доступ ко всему, поэтому он обкладывается обязательными гарантиями (без них вариант небезопасен):
- **Хранилище ключей мастера всегда зашифровано** под ключ мастера (защищён паролем, позже YubiKey). В открытом виде ключи не лежат нигде и на сервер не попадают.
- **Мастер-аккаунт — самое ценное:** сильный пароль обязателен сейчас; YubiKey для мастера — в первую очередь, когда появится.
- **Зашифрованная резервная копия** хранилища ключей мастера, хранится отдельно. ⚠️ Потеря мастер-ключа без копии = потеря доступа ко ВСЕМ данным компании.
- **Позже — Shamir «N из M»** для мастер-ключа: и защита (в одиночку не угнать/не собрать), и восстановление (двое доверенных соберут).
- **Опасные операции мастера** — по кворуму (сейчас 1, позже N из M) и всегда в журнал.

## Платные функции и лицензии (без «звонков домой»)
- Функции включаются по **лицензии**. Уровни лицензии = разный набор функций.
- Лицензия — это **офлайн-файл, подписанный нашим ключом**; программа проверяет подпись встроенным публичным ключом. **Никаких обращений к нам по сети** → не течёт информация о том, кто и как пользуется. Это согласуется с принципом «ноль следов».

## «Ноль следов» — как именно (сводим воедино)
- **Снаружи:** сервиса «не существует» для сканеров (WireGuard + SPA + mTLS); нет публичного домена/SSL.
- **На сервере:** только шифротекст + минимум метаданных; лишнее не храним; логи без чувствительного.
- **На клиенте:** нет открытых копий, кэша, истории на диске.
- **Метаданные:** минимизируем «кто→кому→что», по возможности выравниваем размеры (padding).
- **Что СОХРАНЯЕМ:** зашифрованный tamper-evident журнал действий — **внутри каждой организации, под контролем её админа**. Это функция и требование ФЗ-152, а не утечка.
- **Позже (продвинутый этап):** защита от анализа трафика (нельзя понять даже сам факт связи). В v1 не входит — делаем поэтапно.

## Из чего состоит система (карта модулей)
| Модуль | Роль | Технология |
|---|---|---|
| **Клиент** | вход, формы, шифрование на устройстве, синхронизация, админ-настройки | Tauri (Rust + React/TS) |
| **crypto-core** | общая криптография для клиента и утилит | Rust-крейт (age/libsodium) |
| **Сервер-API** | приём/выдача шифротекста, mTLS, маршрутизация по организациям, дозапись журнала. Ничего не расшифровывает | Rust (axum) |
| **Хранилище** | метаданные и конверты — БД; файлы — объектное хранилище | PostgreSQL + MinIO/ФС |
| **Инфраструктура** | закрытая сеть, шифрование диска, бэкапы | WireGuard, fwknop, nftables, LUKS2, restic+age |
| **Лицензирование** | офлайн-ключи функций | подпись/проверка (Ed25519) |

## Что это меняет в плане реализации
Порядок из 07 остаётся, но Этап 1 (крипто-ядро) сразу проектируем **с учётом организаций и пространств**, а роли/лицензии — как настраиваемые модули. «Заложить сейчас» = заложить понятия tenant/space/роли-права в модель данных, а не дописывать потом.

## Продуктовые уточнения (спека экранов)
- **Бренд:** синий (логотип SecureVault в корне проекта — `logo black.png` для тёмной, `logo white.png` для светлой). В приложении — переключатель темы.
- **Вход единый** для всех ролей (мастер / полный доступ / обычный). **Регистрации нет.** Мастер-аккаунт выдаём мы (вендор) вручную; позже — регистрация через наш сайт (сайт будет, но потом). Сейчас — один клиент, владелец контролирует всё.
- **На экране входа** — без маркетинга и ФЗ; определяем подключённые флешку/YubiKey и авто-выбираем доступный способ (не подключено → «не обнаружено»).
- **Дашборды по ролям с настраиваемыми вкладками.** Типы документов/вкладок настраивает мастер-аккаунт (годится не только для ресторанов): напр. еженедельные/ежемесячные отчёты, зарплаты, авансы; сканы — расписки, подотчётные средства, заявки на наличные.
- **История обязательна** везде: что отправлено, когда, имя файла/документа.
- **Excel-документы правятся прямо в приложении**, правки версионируются и видны.
- **Права на данные:** директор видит/качает только своё; свои сканы может удалять, а правящиеся документы — нет. Полный доступ — максимум (читать/править/удалять/комментировать/качать по всем).
- **Чат** по каждому ресторану с руководством (руководство видит все чаты).
- **Настройки у каждого свои:** тема, личные данные, данные юрлица, название, оповещения. Права/роли/ключи — только в мастер-аккаунте.
- **Мастер-аккаунт** не смотрит отчёты компании; управляет ролями/правами (конструктор ролей), профилями (имя, фото, возможности ключа), выпуском/заменой/отзывом/удалением ключей и связями «кто что видит».
- **KPI-карты/дашборды возможны**, но считаются **на клиенте после расшифровки** (сервер данных не видит): у директора — по своим, у полного доступа — по всем. Серверной аналитики по зашифрованным данным нет.
