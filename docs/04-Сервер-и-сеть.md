# 04 · Сервер и сеть

## Ответ на вопрос: шифровать на сервере или отправлять зашифрованным?

**Отправлять уже зашифрованным (на клиенте).** Если шифрует сервер — на сервере есть ключ и открытые данные в памяти, и захват сервера = утечка. Клиентское шифрование (zero-knowledge) — единственный способ, при котором захваченный сервер бесполезен. Шифрование диска сервера (LUKS) — дополнительный слой, не замена.

## Можно ли зашифровать уже существующий сервер?
- **Да, in-place:** `cryptsetup reencrypt --encrypt` шифрует раздел без переустановки. **Рискованно** — при сбое питания возможна потеря данных. Только с полным бэкапом и простоем.
- **Правильнее:** поставить сервер заново с LUKS с нуля, затем залить данные. Чисто, без риска.
- Раз сервер физический и у нас — выбираем чистую установку с LUKS.

## Шифрование диска сервера (LUKS2)

```bash
# при установке: весь диск (или раздел с данными) под LUKS2
cryptsetup luksFormat --type luks2 \
  --cipher aes-xts-plain64 --key-size 512 \
  --pbkdf argon2id /dev/sdX

cryptsetup open /dev/sdX cryptroot
# далее ФС поверх /dev/mapper/cryptroot
```

### Проблема перезагрузки и её решение
Зашифрованный диск требует ключ при каждом старте. Для сервера без монитора:
- **dropbear-initramfs** — мини-SSH в initramfs. После ребута подключаешься по SSH и вводишь пароль LUKS удалённо.
```bash
apt install dropbear-initramfs cryptsetup-initramfs
# положить свой публичный ключ в /etc/dropbear/initramfs/authorized_keys
# после ребута:  ssh -p <port> root@server  →  cryptroot-unlock
```
- Ключ LUKS **не хранится** на сервере. Пока сервер выключен — диск нечитаем.

## Сеть: сервер-«призрак»

### 1. WireGuard — закрытый контур
Весь доступ к API только изнутри WireGuard. Наружу API не смотрит вообще.
```
[клиент] --wg0--> [сервер:внутренний IP:api]
```

### 2. Single Packet Authorization (fwknop)
Порт WireGuard закрыт в firewall по умолчанию. Открывается на несколько секунд только после валидного зашифрованного SPA-пакета от своего.
```bash
apt install fwknop-server
# сервер: default-drop; fwknopd открывает порт по HMAC-подписанному пакету
# клиент: fwknop -n server  → затем поднимает WireGuard
```
Итог: скан портов из интернета видит **закрытые/отсутствующие порты**. Существование сервиса не выдаётся.

### 3. Firewall (nftables), политика default-drop
```
input policy drop;
разрешить: established/related, loopback
разрешить: SPA-порт (fwknop слушает пассивно)
всё остальное — drop, без ответа
```

### 4. mTLS
Каждое устройство (директора/админа) имеет клиентский сертификат. API отвечает только при валидном клиентском сертификате. Нет сертификата — нет даже разговора.

## Хранилище на сервере
- **PostgreSQL** — метаданные, конверты, мелкие зашифрованные записи. (Данные и так шифрованы на клиенте; можно дополнительно включить шифрование на уровне БД.)
- **MinIO / файлы** — зашифрованные файлы и сканы.
- Сервер оперирует только blob'ами — не знает, что внутри.

## Анонимность vs ФЗ-152 (зафиксировать при старте)
- Сервер физический и в РФ → законный доступ к железу возможен, но при zero-knowledge читать нечего без клиентских ключей.
- Зарплаты/ФИО = персональные данные → хранение в РФ, доступ по журналу. Это осознанный выбор в пользу юридической чистоты.
