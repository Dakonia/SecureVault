# 02 · Стек технологий

Формат: **компонент → что берём → почему → альтернатива**.

## Клиентское приложение (программа директора и админа)
- **Tauri** (Rust + веб-UI) — десктоп-приложение под Windows/macOS.
  - Почему: лёгкое (в отличие от Electron), нейтральное имя/иконка, нет следов браузера, встроенная работа с системным крипто и файлами.
  - Альтернатива: Electron (тяжелее, больше следов), нативный Qt (дольше разработка).
- **UI: React + TypeScript** (или Svelte).
  - Почему: быстрая разработка форм ввода отчётов, таблиц, дашбордов.
- **Встроенный/системный WireGuard-клиент** — туннель до сервера.

## Криптография (сердце системы)
- **libsodium** (через `sodiumoxide`/`libsodium-sys` в Rust, либо `age`).
  - Шифрование данных: **XChaCha20-Poly1305** (потоковое, с проверкой целостности).
  - Конверты (обмен ключами): **crypto_box / sealed boxes** (X25519).
  - Почему: проверенная, аудированная библиотека, «защита от дурака» в API.
- **age** (age-encryption.org) — как более простой вариант конвертов и файлов.
  - Почему: простой формат, есть `age-plugin-yubikey` — привязка расшифровки к YubiKey.
  - Рекомендация: начать с `age` + `age-plugin-yubikey`, это быстрее всего даёт рабочую zero-knowledge схему.
- **Shamir Secret Sharing** для мастер-ключа «2 из 3»: `ssss`, либо SLIP-0039, либо встроить в код через библиотеку.

## Ключи доступа (железо)
- **YubiKey 5** (FIDO2 + PIV) — для 3 человек с полным доступом (обязательно) и, по бюджету, для директоров.
  - Расшифровка привязана к ключу через `age-plugin-yubikey` (identity нельзя извлечь).
- **USB-флешка с age-identity + passphrase** — бюджетный вариант для директоров.
  - Минус: identity-файл копируется вместе с флешкой, поэтому обязателен PIN/passphrase.

## Сеть (невидимость)
- **WireGuard** — закрытый шифрованный контур. Весь доступ только внутри него.
- **fwknop (Single Packet Authorization)** — сервер не открывает даже WireGuard-порт, пока не придёт «секретный пакет». Для сканеров портов не существует.
  - Альтернатива: классический port knocking (проще, но слабее).
- **nftables** — firewall с политикой default-drop. Наружу закрыто всё.

## Сервер
- **ОС: Debian 12 или Ubuntu Server LTS** — стабильность, свежий cryptsetup/WireGuard.
- **LUKS2** (aes-xts-plain64, аргон2id) — шифрование всего диска.
- **dropbear-initramfs** — удалённый ввод ключа LUKS по SSH при перезагрузке.
- **API-бэкенд: Rust (axum) или Go** — минимальный сервис: принять/выдать шифротекст, проверить mTLS. Ничего не расшифровывает.
- **PostgreSQL** — метаданные, конверты, мелкие зашифрованные записи.
- **MinIO** (или просто файловое хранилище) — зашифрованные файлы/сканы.
- **mTLS (клиентские сертификаты)** — каждое устройство имеет свой сертификат; сервер отвечает только «своим».

## Аудит и журнал
- **Append-only audit-log** — записи только добавляются, задним числом не меняются.
- Подпись цепочки записей (hash-chain), чтобы нельзя было незаметно вырезать строку.

## Бэкап
- **restic** + шифрование через **age** — инкрементальные зашифрованные бэкапы.
- Ключ бэкапа хранится **отдельно** от сервера и от бэкапа (иначе смысла нет).
- Хранилище бэкапа: второй носитель / другое хранилище (учесть ФЗ-152 — РФ).

## OCR и разбор документов (опционально, позже)
- **Tesseract** или **PaddleOCR** — локально, на клиенте или в закрытом контуре.
  - Почему локально: распознавание расписок/чеков не должно уходить во внешние сервисы.

## Аналитика (осторожно)
- Дашборды строятся **после расшифровки на клиенте** полного доступа, либо на отдельных согласованных агрегатах.
- **Metabase** — только если решим часть неконфиденциальных агрегатов держать доступными серверу (это отход от строгого zero-knowledge, решать отдельно).

## Чего НЕ используем
- ❌ Внешние LLM-API (YandexGPT/Claude) на конфиденциальных данных — противоречит секретности.
- ❌ Публичный домен с SSL-сертификатом — попадает в Certificate Transparency, выдаёт существование.
- ❌ Самописную криптографию — только проверенные библиотеки.
